# 주문 할인 계약 초안

## 1. 문서 목적과 출처

이 문서는 쿠폰 할인을 구현하는 문서가 아니다. 요구에서 확인된 제품 약속, 이번 실습에서만 사용할 조건, 제품 담당자의 답이 필요한 질문을 분리하고 다음 구현 단계에서 테스트로 옮길 계약을 정리한다.

> 기준 문장: “구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다.”

- 출처: 제품 담당자와 범위를 확인한 뒤, 기준 문장을 고친 내용
- 문서 기준 revision: Kotlin `807c3f87114d2bef4fcfb27333df93d5706d4fe2`

### 2.4 출처 없는 제안 처리


- 별도 멱등성 키 도입은 같은 주문·쿠폰 재요청이라는 조건보다 저장 방식과 보관 정책을 더 많이 요구함: 거절
- 주문 취소 후 쿠폰 복원은 쿠폰 상태와 주문 취소 이력의 의미를 바꾸지만 현재 요구에 근거가 없음: 보류
- 쿠폰 1회 사용, 교체 거절, 만료 등호 경계, 금액 초과 처리, 소유권 오류 구분은 모두 제품 확인 전: 임시안
- 오류 code 문자열과 내부 책임 이름은 학습자가 선택할 기술 계약임: 거절

## 4. 외부 API 계약

### 4.1 요청

- Method: `POST`
- Path: `/api/v1/orders/{orderId}/discount`
- 사용자 식별: `X-USER-ID` header의 사용자 ID
- Request body:

```json
{
  "couponId": 123
}
```

기본 장면과 비교해 method, path, `couponId` body는 동일하다. 같은 요청은 별도 키가 아니라 `orderId + couponId`로 식별하고 `X-USER-ID`로 소유권을 확인한다.

### 4.2 성공 응답

동일한 요청을 재전송한 경우에도 최초 확정 결과를 같은 형태로 반환한다.

```json
{
  "meta": {
    "result": "SUCCESS",
    "errorCode": null,
    "message": null
  },
  "data": {
    "orderId": 10,
    "originalAmount": 10000,
    "discountAmount": 2000,
    "finalAmount": 8000
  }
}
```

### 4.3 오류 의미

아래 code는 제품 정책이 아니라 다음 구현 단계에서 실패 원인을 테스트하기 위한 외부 계약 초안이다. 실패 응답의 `meta.result`는 `FAIL`이고 `data`는 `null`이다.

| HTTP status | `meta.errorCode` | 의미 |
|---:|---|---|
| 400 | `INVALID_REQUEST` | header/body가 없거나 타입·형식이 잘못됨 |
| 401 | `AUTHENTICATION_REQUIRED` | 사용자 식별 정보가 없음 |
| 403 | `ORDER_NOT_OWNED` | 요청 사용자가 주문 구매자가 아님 |
| 403 | `COUPON_NOT_OWNED` | 쿠폰 소유자가 요청 사용자와 다름 |
| 404 | `ORDER_NOT_FOUND` | 주문을 찾을 수 없음 |
| 404 | `COUPON_NOT_FOUND` | 쿠폰을 찾을 수 없음 |
| 409 | `ORDER_ALREADY_CONFIRMED` | 이미 확정된 주문에 새로운 할인을 적용하려 함 |
| 409 | `COUPON_EXPIRED` | 요청 시작 시각 기준으로 쿠폰이 만료됨 |
| 422 | `COUPON_ALREADY_APPLIED` | 한 주문에 쿠폰 한 장이라는 적용 규칙을 위반함 |
| 422 | `COUPON_ALREADY_USED` | 쿠폰 1회 사용이라는 임시 적용 규칙을 위반함 |
| 500 | `INVALID_DISCOUNT_POLICY` | 계산 할인액이 음수인 등 사용자가 고칠 수 없는 쿠폰 정책 오류 |

## 5. 외부 계약과 내부 경계 결정

### DEC-001: HTTP status와 안정적인 error code를 함께 사용한다

- 선택: HTTP status는 오류의 큰 범주를, `meta.errorCode`는 클라이언트가 분기할 구체적 원인을 표현한다. 시간이나 주문 상태 변화로 현재 요청과 충돌하면 409, 쿠폰 사용 횟수나 주문당 쿠폰 수 같은 적용 규칙 위반은 422로 분류한다.
- 버린 대안: 모든 도메인 실패를 `400 Bad Request` 하나로 반환한다.
- 이유: 만료, 소유권 위반, 확정된 주문, 쿠폰 사용 규칙 위반을 요청자의 다음 행동에 맞게 구분할 수 있다. 구체적인 원인은 error code로 안정적으로 식별한다.

### DEC-002: 확정된 할인 금액을 snapshot으로 보존한다

- 선택: 확정 시점의 `originalAmount`, `appliedDiscountAmount`, `finalAmount`, `couponId`, 적용 기준 시각을 결과에 보존한다.
- 버린 대안: 주문 조회 때마다 현재 쿠폰 정보로 할인액을 다시 계산한다.
- 이유: 재계산은 쿠폰 정책이나 데이터가 바뀌었을 때 `FACT-002`와 `INV-004`를 깨뜨린다.

### DEC-003: 하나의 주문 할인 유스케이스가 호출 순서와 원자성을 숨긴다

- 선택: Controller는 입력 변환과 응답 변환만 담당한다. 주문 할인 유스케이스가 요청 시작 시각 포착, 기존 할인 결과 조회, 주문·쿠폰 조회, 권한·상태·만료 검증, 금액 계산, snapshot 확정 순서를 숨긴다. 구체적인 클래스와 트랜잭션 구현은 이번 문서에서 정하지 않는다.
- 버린 대안: Controller가 주문 서비스와 쿠폰 서비스를 순서대로 직접 호출한다.
- 이유: 호출 순서와 부분 실패 처리가 HTTP 계층에 노출되면 중복 처리와 원자성 규칙을 한곳에서 보장하기 어렵다.

## 6. 명시적 비범위

- 이번 주에는 `apps/commerce-api/src/main/**`를 수정하지 않는다.
- 쿠폰·주문 엔티티, 데이터베이스 schema, repository, transaction 구현을 만들지 않는다.
- 제품 담당자의 답이 없는 임시안을 실제 제품 정책으로 확정하지 않는다.

## 7. 다음 구현 단계 인계 요약

다음 구현 단계에서는 `INV-001..007`을 같은 ID와 의미로 테스트 이름 또는 테스트 설명에 연결한다. 구현 전에는 먼저 `Q-001..005`의 제품 답변을 받아 임시안을 유지·수정·폐기한다. 답을 받을 수 없다면 임시안임을 테스트와 코드 설명에 남긴다.
