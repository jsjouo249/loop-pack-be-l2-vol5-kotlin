# 3주차 설계 결정과 검증 기준

## 1. 현재 결정 상태

기준 revision과 요구·검증 계획은 [작업 계획](implementation-plan.md)을 따른다.
초기 제안에 대한 사용자 답변을 반영했다. 확정된 선택을 다시 미결정 질문으로 반복하지 않는다.
아래 확정 결정을 운영 코드·테스트에 반영했다. 실제 MySQL 검증도 완료했고
[실행 기록](verification-report.md)에 단위/정적 검사와 구분해 기록한다.

| ID | 사용자 답변 / 현재 선택 | 상태 |
|---|---|---|
| D1 | 비관적 잠금 사용. 결제 정합성을 구현 시작부터 보장 | 사용자 확정 |
| D2 | User 생성 시 PointAccount 동시 생성, 기존 누락은 0으로 보정, 이후 누락은 무결성 오류 | 사용자 확정 |
| D3 | 작업별 저장 계약 분리, 필요한 경우만 사전 잠금 | 사용자 확정, [상세 설계](backend-design.md)에 구체화 |
| D4 | 보호하는 쓰기 유스케이스 공통 deadlock 1회 재시도·50ms 대기, 확인된 잠금 실패는 503 TRANSACTION_BUSY | 사용자 확정, [오류 처리 정책](transaction-error-policy.md) |
| D5 | 상품 등록도 브랜드 삭제와 같은 보호 규칙에 참여 | 사용자 확정, 선택 확장을 이번 범위에 포함 |
| D6 | domain 행동과 rollback 증명에 집중 | 사용자 확정, bulk SQL을 기본 방식으로 도입하지 않음 |

D1~D6와 후속 적용 범위·50ms 결정이 완료되었고 요구사항을 막는 미결정 사항은 없다.
저장 메서드·SQL 방식·잠금 범위·시간 설정·API 계약은 [Backend 상세 설계](backend-design.md)로 구체화했다. 새 회원가입 API와 운영 migration은
이번 범위에 추가하지 않는다. 이 문서 갱신은 실제 DB 보정이나 코드 구현을 수행했다는 뜻이 아니다.

## 2. D1 — 비관적 잠금 사용

- `[사용자 결정]` 주문 상태·재고·포인트의 읽기·판단·변경에 비관적 잠금을 적용한다.
- `[사용자 근거]` 결제 관련 정합성은 성능 측정 후 보완할 수 있는 문제가 아니다.
- `[설계 해석]` 동의한다. 정합성은 최초 구현의 필수 조건이다. 낙관적 잠금·조건부 갱신도
  올바르게 설계하면 정합성을 보장할 수 있으므로, 비관적 잠금만 결제에 안전하다고 일반화하지 않는다.
- 잠금과 상태 변경은 같은 application transaction에 두고, 주문·포인트·상품의 모든 관련
  쓰기 경로를 점검한다. 전역 synchronized, 잠긴 행을 품절로 처리하는 SKIP LOCKED는 사용하지 않는다.
- 감수할 비용: 잠금 대기·connection 점유·교착 가능성. 처리량 우월성은 아직 측정하지 않았다.

기술 근거: [MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html).

## 3. D2 — 사용자와 포인트 계정 동시 생성

### 확정된 생성 계약

사용자 계정을 User로 해석한다. 사용자 생성 시 잔액 0인 PointAccount를 같은 transaction에
생성하면 충전·결제 시점에 잠글 행이 존재한다. User와 PointAccount는 별도 Aggregate로 유지하고
application이 생성을 조율한다. User repository의 내부 부작용이나 JPA callback으로 숨기지 않는다.

```text
사용자 초기화 application transaction
  User 저장 → PointAccount(userId, balance=0) 저장 → 함께 commit
  PointAccount 저장 실패 → User 생성도 rollback
```

### 기존 구현과 달라지는 계약

| 현재 2주차 | 확정된 3주차 계약 |
|---|---|
| 계정 행 부재를 정상 잔액 0으로 처리 | 정상 사용자는 생성 완료 시 포인트 행 하나를 보유 |
| 첫 충전에서 PointAccount 생성 | 충전은 기존 PointAccount를 잠근 뒤 충전 |
| 0원 주문은 계정 없는 상태로 확정 | 이미 존재하는 계정을 유지하고 잔액 0 그대로 확정 |
| 테스트가 UserJpaRepository에 직접 사용자 insert | 공통 초기화 경로 또는 동일 계약의 fixture로 User·PointAccount 함께 준비 |
| 계정 부재 첫 충전 경쟁 검증 필요 | 사용자·포인트 생성 원자성 및 기존 계정의 충전 경쟁 검증 필요 |

`[코드 확인]` 사용자 생성 HTTP API는 없다. UserRepository.save 계약은 있지만 현재 HTTP
테스트는 UserJpaRepository에 직접 저장한다. import.sql은 FK DDL이며 사용자 seed가 아니다.

### 확정된 전환 범위

- `[사용자 결정]` 신규 회원가입 HTTP API를 추가하지 않고, 내부 application 초기화 경로와 fixture를
  마련한다. 실제로 사용하는 경로에서 두 저장을 묶고 생성 실패 rollback을 검증한다.
- `[사용자 결정]` 이전 데이터에서 누락된 계정은 잔액 0으로 보정하되 존재하는 잔액은 덮어쓰지 않는다.
  보정은 충전·결제의 상시 fallback과 분리한 전환 작업으로 다룬다. 반복 실행해도 기존 잔액을
  바꾸지 않음을 검증한다. 현재 로컬·테스트는 ddl-auto=create이며 실제 보정 경로는 실행 환경에 맞춘다.
- `[사용자 결정]` 전환 뒤 예상치 못한 계정 부재는 무결성 오류로 처리한다. 잔액 조회·충전·결제에서
  정상 잔액 0으로 숨기거나 자동 생성하지 않는다. 기존 500 응답을 사용하고 내부 원인을 기록한다.
- 물리 FK와 User당 포인트 계정 존재 보장은 별개다. FK 추가만으로 모든 User의 계정 생성이
  보장되는 것은 아니다. 기존 user_id PK로 중복을 막고 생성 경계로 누락을 방지한다.
- User를 포인트 조정용 잠금 대상으로 사용하는 초기 추천은 폐기한다.
  포인트 쓰기는 PointAccount 행을 공통으로 잠근다.

## 4. D3 — 작업별 저장 계약 분리

`[사용자 결정]` domain 전체 snapshot을 모든 변경에 다시 저장하는 방식을 작업별 계약으로 나눈다.
이름 수정이 재고를, 삭제가 가격을, 브랜드 이름 수정이 삭제 상태를 덮어쓰지 않아야 한다.

| 작업 | 저장이 변경할 상태 | 유지할 책임 |
|---|---|---|
| 상품 생성 | 새 상품의 초기 상태 | Product 생성 검증 |
| 상품 이름·가격 수정 | 이름·가격 및 필요한 수정 시각 | Product.changeDetails의 값 검증, 삭제 상품 수정 거절 |
| 관리자 재고 설정 | 최종 재고 및 필요한 수정 시각 | Product.adjustStock, 삭제 상품 거절, 주문과 공통 잠금 |
| 주문 재고 차감 | domain이 차감한 재고 및 필요한 수정 시각 | Product.decreaseStock, 잠금 후 최신 재고 검증 |
| 상품 개별/일괄 삭제 | 삭제 상태 및 필요한 수정 시각 | Product.delete, 기존 주문·좋아요 관계 보존 |
| 브랜드 이름 수정 | 이름 및 필요한 수정 시각 | Brand.rename, 삭제 브랜드 수정 거절 |
| 브랜드 삭제 | 삭제 상태 및 필요한 수정 시각 | Brand.delete, 상품 등록과 공통 보호 |
| 주문 확정 저장 | 상태·결제 결과·확정 시각 | Order.confirm, 품목·가격 snapshot 불변 |
| 포인트 잔액 저장 | 잔액 | PointAccount의 충전·결제 규칙, 공통 행 잠금 |

위 표는 변경 책임이며 메서드명·parameter 및 SQL 규칙은 [상세 설계 §3](backend-design.md)에 명시한다. domain repository
계약부터 중립 저장 데이터와 JPA 구현까지 연결하되, application/domain에 JPA 타입을 노출하지 않는다.

부분 갱신은 비관적 잠금을 대체하지 않는다. 특히 재고끼리, 잔액끼리의 경쟁과 삭제 여부 판단을
보호해야 한다. 상품 정보 변경도 삭제와의 순서를 보호하되, unrelated 필드를 쓰지 않는다.
`@DynamicUpdate`만 추가하고 오래된 값을 updateFrom으로 다시 넣는 방식은 이 결정을 충족하지 않는다.

### 필요한 잠금만 적용하는 순서

```text
Order → PointAccount → Brand → Product(ID 오름차순)
```

| 유스케이스 | 명시적 사전 잠금 순서 |
|---|---|
| 주문 확정 | Order → PointAccount → Product ID순 |
| 포인트 충전 | PointAccount |
| 브랜드 일괄 삭제 | Brand → 대상 Product ID순 |
| 상품 등록 | Brand 활성 상태 잠금 조회 → 새 Product 저장 → commit까지 유지 |
| 브랜드 이름 수정 | 없음. 활성 조건 name 전용 UPDATE |
| 상품 정보/최종 재고/개별 삭제 | 없음. 활성 조건의 작업별 단건 UPDATE |

- 쓰지 않는 자원까지 잠그지 않는다. User 조정용 잠금은 제외한다. 표의 사전 잠금 없음은
  DML의 DB 쓰기 잠금이 없다는 뜻이 아니다. 단건 UPDATE가 삭제/주문의 잠금과 순서를 정한다.
- 상품 수정 후 브랜드 응답 조합에 역순 잠금을 추가하지 않는지 확인한다.
- 브랜드 잠금 대기 후 대상 상품은 등록의 최신 commit을 포함하는 조회로 수집해야 한다.
  이전 비잠금 snapshot을 재사용하면 공통 Brand 잠금만으로 충분하지 않다.
- IN 인자의 정렬만으로 DB 잠금 순서를 단정하지 않는다. 실제 쿼리와 FK·인덱스의 잠금까지 검토한다.
- 잠금 획득 순서 때문에 기존 업무 오류 우선순위를 불필요하게 바꾸지 않는다.

기술 근거: [MySQL 교착 방지와 처리](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks-handling.html).

## 5. D4 — 확정된 오류·재시도 정책

상세 근거와 검증은 [오류 처리 정책](transaction-error-policy.md)을 따른다.

1. 보호하는 쓰기 유스케이스에 전체 rollback 확인 deadlock 최대 1회 재시도를 공통 적용한다.
   최초 포함 총 2회이며, 자원 반환 후 고정 50ms 대기하고 새 transaction에서 전체를 재조회한다.
   원래 대상은 상세 설계의 쓰기 API 8개이며 리뷰 보완에서 좋아요 등록·취소를 추가해 총 10개다. 읽기·단순 초기 생성 등에 무차별 적용하지 않는다.
2. lock timeout은 유스케이스 전체 rollback 후 자동 재시도 없이 실패한다. 업무 거절·버그·
   무결성 오류·commit 결과 불명도 재시도하지 않는다.
3. rollback이 확인된 lock timeout과 deadlock 재시도 소진은 `503 TRANSACTION_BUSY`다.
4. 재시도 중 재고·잔액 부족 또는 이미 확정이면 해당 기존 업무 오류를 반환한다.
   commit 결과 불명·프로그램/무결성 오류는 기존 500이며 잠금 실패로 위장하지 않는다.
5. 원 요청 결과와 내부 시도별 오류를 분리 기록한다. 503은 충전 요청의 무조건 재전송 허가가 아니다.

## 6. D5 — 상품 등록과 브랜드 삭제를 같은 보호 규칙에 포함

`[사용자 결정]` 과제의 선택 확장을 이번 작업 범위에 포함한다.

- 상품 등록과 브랜드 삭제가 동일 Brand 행을 잠그고 활성 여부를 판단한다.
- 등록이 먼저 완료되면 새 상품도 이어지는 삭제 대상에 포함된다.
- 삭제가 먼저 완료되면 등록은 기존 BRAND_NOT_FOUND로 거절되고 상품은 생성되지 않는다.
- 양쪽 모두 잠금을 얻은 뒤 현재 상태를 사용하며 transaction 종료까지 유지한다.
- 기존 Product 행의 잠금뿐 아니라 삭제 대상 집합을 변경하는 생성 경로도 보호한다.
- 같은 브랜드의 상품 등록을 직렬화하는 비용을 감수한다. 실제 순서와 결과는 MySQL 테스트로 확인한다.

두 직렬 순서 및 동시 실행 뒤 최종 상태를 검증한다. 운영 코드에 테스트 장벽을 추가하지 않는다.
현재 요구에 없는 다른 경쟁 조합까지 검증했다고 주장하지 않는다.

## 7. D6 — domain 행동과 rollback 증명에 집중

`[사용자 결정]` Product 삭제 행동과 명시적 저장을 사용하며, bulk UPDATE 성능 실험은 이번 범위에 넣지 않는다.
D3의 부분 갱신은 바꿀 필드를 좁히는 계약이고, D6의 bulk 제외는 여러 행의 domain 행동을 생략하지
않겠다는 선택이다. 두 결정은 함께 적용할 수 있다.

- 관련 상품 모두에 domain 삭제 행동을 요청하고 작업별 삭제 저장 계약으로 반영한다.
- 전체 작업은 하나의 transaction으로 유지한다. 상품별·청크별 독립 commit은 사용하지 않는다.
- 중간 실패 테스트에서 앞 변경의 SQL 전송과 유스케이스 종료 후 전체 rollback을 증명한다.
- 큰 브랜드의 객체 로딩·잠금 시간은 아직 측정되지 않은 한계로 기록한다.

## 8. 반례 확인 결과와 구현 인계

초기 선택 이후 한 차례의 확인에서 사용자는 다음을 확정했다.

1. 누락된 기존 포인트 계정은 0으로 보정하고 이후 누락은 오류로 처리한다.
2. rollback이 확인된 deadlock은 새 transaction으로 1회만 재시도한다.
3. 확인된 일시적 잠금 실패는 기존 500과 구분한 503 오류 계약을 사용한다.

후속 답변에서 사용자는 공통 재시도 범위, 50ms 간격, 필요한 잠금만 적용하는 상세화와
별도 계정 보정 경로도 확정했다. 상세 설계는 완료됐으며 구현을 막는 제품 정책 질문은 없다.
예외 판별·SQL·rollback·시간 설정의 실제 효과는 구현 후 Spring/JPA/driver와 MySQL 테스트로
검증한다. 문서 확정이 실행 검증 완료를 뜻하지는 않는다.

|---|---|---|---|
| D1 | 비관적 잠금 | 잠금 대기·교착 가능성, 낙관적/조건부 차감 제외 | 실제 DB 검증 통과, 실행 기록 참조 |

| D3 | 작업별 저장 계약 | 계층별 계약·매핑 변경, 전체 snapshot 덮어쓰기 폐기 | 실제 DB 검증 통과, 실행 기록 참조 |

단위 테스트와 실제 DB 테스트의 상태는 [실행 기록](verification-report.md)을 따른다.
